## 实测结论（macOS 26，14" MBP 1470x956，刘海 179x32 中心 x=735）

1. **所有菜单栏状态项窗口 owner 都是"控制中心"**（第三方 NSStatusItem 也被托管），
   无法按 pid 区分自己的项；层固定为 25（kCGStatusBarWindowLevel），菜单栏背景是 24 层整条窗口。
2. **macOS 永远不会把状态图标排到刘海左侧**：左侧是应用菜单领地；溢出图标被系统直接隐藏，
   连 CGWindowList 的 on-screen 列表都会消失（`optionOnScreenOnly` 拿不到）。
   用户截图里"刘海左边的半个图标"是贴顶的桌面歌词窗，不是状态项。
3. **隐形加宽 NSStatusItem 占位（Hidden Bar 同款机制）**：插入后系统把可移动图标簇的
   左端前缀挤进刘海隐藏，移除占位后原图标原样恢复。但重排**量化且懒执行、多数情况不触发**：
   - NSStatusItem 窗口宽 ≈ length + 16（系统边距）；
   - 占位宽度 ≤ 刘海与图标簇的现有空隙（约 38~40pt）时被完全吸收，图标纹丝不动；
   - 唯一一次位移成功（w=75，吞掉 3 个图标）疑似酷狗歌词状态项自身变宽造成的假阳性。
4. **冲突源主要是酷狗歌词状态项，宽度随歌词行实时变化**（30~170pt 之间跳），
   任何"一次算准宽度"的公式都会失效，只能实测反馈 + 稳定性等待。

## 当时实现的状态机（ IslandController.updateMenubarYield，已回滚）

```
音乐收起态 → 探测冲突(与满配岛体 38/44 相交的右侧簇前缀)
  ├─ 无冲突(已让路) → 岛展开满配；明显过度隐藏(首个可见图标比预期靠右>48pt)则收窄占位
  ├─ 冲突图标宽度还在变 → 等一拍，不追
  ├─ 占位未到顶(prefixSpan+60 与 yieldMaxWidth=140 取小) → 每拍 +16 加宽
  │    首步宽度 = max(prefixSpan+4, 空隙+prefixSpan+4)；窗口宽 = length+16
  ├─ 到顶后保持 20s 等系统的懒执行隐藏；期间岛保持收缩翼展（绝不出现覆盖窗口期）
  └─ 超时 → 撤占位 + 冷却 30s + 回退"两翼收缩 + 黑底补平衡"方案
占位窗口识别：按 CGWindowNumber（Swift 里叫 kCGWindowNumber）追踪，
发现条件 = "宽度匹配 ±3 且（新出现 或 宽度刚变化）"——按宽度常驻匹配会误伤宽度相近的真实图标
（实测 36 占位 vs 32 图标）。
```
